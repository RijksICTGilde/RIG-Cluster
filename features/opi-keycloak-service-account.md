# OPI Keycloak Service Account (client-credentials)

## What it is

OPI previously authenticated to the Keycloak master realm with the shared
`admin` username + password. That meant the `admin` account could not be
OTP-enforced or locked without locking OPI out. OPI now authenticates with its
own **client-credentials service account** (a confidential client in the master
realm with the master `admin` role), so its automation is independent of any
human-admin OTP policy.

Because OPI uses the token endpoint (not the browser flow), and now a dedicated
machine identity, you can enforce OTP on the human `admin` account and create
separate OTP-enabled human admins without affecting OPI.

## This is the prerequisite, not the whole story

This service account is the foundation the rest of the Keycloak-hardening work
builds on. Keep two distinct OTP concerns apart (see also
[keycloak-realm-admin-otp.md](keycloak-realm-admin-otp.md)):

- **OTP *in* Keycloak** protects the Keycloak console: it makes a leaked admin
  password worthless and blocks brute force at the login screen. It is stored the
  same way as the other secrets and is explicitly *not* protection against an
  adversary who already reached the secret store.
- **OTP *in* ZAD**, on the user table, is the real second factor: it is bound to a
  person, not a shared account, and is where elevated rights are gated. That is a
  separate piece of work.

OPI on a machine identity is what makes the end state reachable where the shared
`admin` account is no longer a daily workhorse but a break-glass account, and
each Keycloak admin has their own account with a person-bound OTP that Keycloak
generates itself. A machine process gets no OTP: a second factor is meaningless
for automation.

## How it works (hybrid self-bootstrap)

On startup (`KeycloakSetup.setup_all` -> `ensure_master_admin_service_account`):

1. If `KEYCLOAK_ADMIN_CLIENT_SECRET` is empty -> OPI stays on admin-password auth (legacy, unchanged).
2. If the secret is set and client-credentials already work -> use them; nothing else to do.
3. Otherwise (fresh cluster) -> OPI uses the admin password **once** to create/repair the master confidential client (`KEYCLOAK_ADMIN_CLIENT_ID`, secret = the configured value, `serviceAccountsEnabled`, interactive flows disabled) and grants its service-account user the master `admin` role.

After the first bootstrap the client exists with a deterministic (bootstrap-provided)
secret, so every later boot authenticates purely via client-credentials. The
admin password can then be removed from OPI's env and OTP-enforced.

All Keycloak access flows through one factory, `create_keycloak_connector()`,
which prefers client-credentials when the secret is set; pass
`use_client_credentials=False` to force the admin-password path (used only for
the first-boot bootstrap and the availability probe fallback). Because it is one
factory, the authentication change lands in a single place and the ~27 callers
are unaffected.

## Configuration

| Setting | Default | Meaning |
|---|---|---|
| `KEYCLOAK_ADMIN_CLIENT_ID` | `opi-admin-service` | Master confidential client id for OPI. |
| `KEYCLOAK_ADMIN_CLIENT_SECRET` | `""` (off) | Client secret. When set, OPI uses client-credentials. |
| `KEYCLOAK_ADMIN_USERNAME` / `KEYCLOAK_ADMIN_PASSWORD` | `admin` / ... | First-boot bootstrap + break-glass only once the secret is set. |

### Where the client secret comes from (bootstrap ordering)

The client secret is generated by the same bootstrap secret template that
generates the admin password:
`infrastructure/bootstrap/infrastructure/secrets/templates/keycloak-admin-secret.yaml`
carries `KEYCLOAK_ADMIN_CLIENT_SECRET` with a `@secret-gen:random:32` annotation,
so `task generate-secrets-for-cluster <cluster>` writes it (SOPS-encrypted)
alongside `KEYCLOAK_ADMIN_PASSWORD` in the `keycloak-admin-credentials` secret.

The order the bootstrap guarantees:

1. The secrets are created first (both admin password and client secret live in
   `keycloak-admin-credentials`, applied before OPI starts).
2. OPI boots and self-bootstraps **once**: it uses the admin password to create
   the confidential client with the generated secret and grant it the `admin`
   role.
3. From then on OPI authenticates purely via client-credentials; the admin
   password is no longer used for day-to-day work.

The deployment injects the client secret with `optional: true`, so a cluster
whose `keycloak-admin-credentials` predates this key (secret not yet
regenerated) keeps working: the env var is unset -> OPI stays on the admin
password until the secret is regenerated. That makes rollout non-breaking.

### What happens to the admin password afterward

This is deliberately explicit so it does not stay implicit and unused-but-present.
After convergence the admin password is **only** first-boot bootstrap and
break-glass:

- Keep the original `admin` super-user as break-glass: password in a vault,
  OTP-enforced, otherwise unused.
- Once a cluster has converged onto client-credentials, remove
  `KEYCLOAK_ADMIN_PASSWORD` from OPI's env in that cluster (a deliberate second
  step via Git -> ArgoCD) and OTP-enforce/lock the `admin` account.

## Operational guidance (human admins + break-glass)

- Keycloak supports **unlimited admin accounts** - admin is just role assignment (master `admin` role for full, or `realm-management` client roles for scoped).
- Create **separate human admin accounts** in the master realm, each with OTP (Keycloak generates the seed; the admin scans the QR - nothing shared is stored).
- Keep the original `admin` super-user as **break-glass**: password in a vault, OTP-enforced, otherwise unused. With OPI on its service account, `admin` is no longer needed for automation.
- Restrict the `/admin` console at the ingress (VPN/allowlist) so password-only exposure isn't internet-reachable.

## Files

- `opi/core/config.py` - `KEYCLOAK_ADMIN_CLIENT_ID/SECRET`.
- `opi/connectors/keycloak.py` - client-credentials mode in `KeycloakConnector.__init__`, factory selection, `connection_works()`, `ensure_master_service_account_client()`.
- `opi/bootstrap/keycloak_setup.py` - `ensure_master_admin_service_account()` (first-boot self-bootstrap).
- `opi/core/startup.py` - availability probe falls back to admin password before the client exists.
- `infrastructure/bootstrap/infrastructure/secrets/templates/keycloak-admin-secret.yaml` - generates the client secret.
- `bootstrap/rig-system/kustomize/operations-manager/overlays/sandboxed-local/patches/deployment.yaml` - env injection.
